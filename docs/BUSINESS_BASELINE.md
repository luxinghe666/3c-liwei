# 现有业务与 UI 2.0 迁移基线

本文件是脱敏开发摘要，不包含真实员工账号、客户资料、订单、资金流水或供应商合同。以当前实现和测试为准，区分已存在能力、最新业务意图和仍需开发的部分；不是替代历史完整需求的重新设计。

## 当前代码结构与能力

| 领域 | 当前源码 | 当前边界 |
| --- | --- | --- |
| 网页 | `dist/index.html`、`app.js`、`erp.*`、`stock-workspace.*`、`employee-profile.*` 等 | 原生 HTML/CSS/JS；业务接口仍由后端鉴权 |
| iPhone | `ios/YuantuoFinance/` | SwiftUI 原生页面、登录、库存/ERP 与财务界面；保留现有工程，不重新搭建正式 App |
| 账本与财务 | `server/book.mjs`、`store.mjs`、`erp-payment.mjs`、`dist/model.js` | 资金流水、往来、费用、关账、更正、对账及利润计算使用既有规则 |
| ERP / SN | `server/erp.mjs`、`dist/stock.js` | 单据、唯一串号、收货/入库/出库/发货和退货记录；部分多 SKU 履约路径仍有限制 |

## 岗位与数据权限

当前服务端角色是老板 `owner`、财务 `finance`、采销 `procurement_sales`、出库入库 `warehouse`。两位运营使用独立账号，同属出库入库岗位，操作记录必须归属实际登录人。

用户计划的 UI 2.0 展示五岗位：老板、客户经理、采购、运营、财务。客户经理和采购拆分是新 UI 设计意图，不表示当前服务端已有两个独立角色。演示可以分开展示工作重点；正式权限拆分需另行确定映射和服务端回归。

- 老板管理成员、权限与关账；财务沿用录入直接生效的规则。
- 采销/运营可以办理获准的业务与库存动作，不能查看全部历史成本、财务及利润。
- 录单时填写本笔必要价格/运费不开放历史金额、利润或账户余额。
- 现有额外能力配置主要是 B 标映射、盘点和集成管理；任意查看/修改/导出以及临时授权不能在 UI 中冒充现有后台能力。
- 企业微信身份、部门及职务与 ERP 权限分开。首次登录建立待分配身份，老板明确授予 ERP 岗位；不得以姓名/手机号相同自动合并或提升权限。

## 订单、库存与资金

1. ERP 是统一采购订单主数据来源。小程序供货商与下游销售客户区分；报价确认应关联唯一 ERP 订单，重试不能新建重复订单。
2. 使用统一 SKU、订单 ID 和订单编号。金额采用整数分，并保持现有接口状态、错误码、签名及幂等约束。
3. 采购单支持多个商品行；付款支持部分支付和一笔流水分配多笔订单。付款状态由已核对的 ERP 资金记录计算，不能只由小程序显示值决定。
4. 小程序已登记的付款凭证须由财务核对：ERP 没有流水时补记一次，已有流水则关联，不自动重复扣款。
5. 订单、付款、物流、收货、入库、出库、发货及退货通过单据和 SN 追溯。创建人、出库人和发货登记人可以不同；分批操作记录各自实际经办人。
6. 库存以型号、数量和唯一串号管理。新的串号货物使用串号实际采购成本；旧数量账本不因开启串号功能自动重估或重写历史成本。
7. 两人同时处理、重复提交和网络重试必须保留原有事务、版本及幂等保护，不超量收发货、不重复记账。
8. 仓库销售按已确认的出库节点形成应收。供应商直发与公司实物仓收发分开表达，不虚增实物库存。
9. 供应商预付款余额和应付款分别显示，由财务明确抵扣；账户内部转账不当作经营收入。
10. 待签合同、待收发票和待开发票状态相互独立。合同拒签、重签和版本历史必须保留，不能以新版本覆盖旧事实。

## 最新意图与未完成事项

- 最新业务意图是“代发入库登记即记应付、供应商发货时记应收”。既有路径不应未经核对就被视为已全部符合；UI 演示可以展示目标状态，不得在本轮更改实际记账节点。
- 多 SKU 建单与付款已存在实现，但 `server/erp.mjs` 对若干履约路径仍有 `requireSingleLine` 保护。不要为了演示批量收发货而删除保护；完整多行按 SN 分配收发需要独立业务开发和回归。
- 已出库销售额减 SN 成本与回款确认利润应分开；UI 2.0 计划同时展示现金利润、内部估算利润、正式财务利润。现有利润名称、公式、税费及日期口径须逐项对应，不能用换标题代替实现三套口径。
- 进项台账独立于实物库存。最新需求允许进项不足时继续出库形成应收、标记票据待补齐，并暂不计算依赖进项均价的估算利润；不能把待设计页面当作已贯通的核算能力。
- 日利润/月利润、月度税费、关账后调整和历史报表沿用原规则。本轮不得迁移或重算生产账本。
- 原操作记录含实际账号和姓名等字段；完整历史头像/昵称/部门快照及长期内部头像版本的覆盖仍应核实，不能用现员工头像冒充历史头像。
- 企业微信网页登录和通知适配不等于 iPhone 原生授权、回跳与会话已经完成。
- WPS 正式 API 授权和同步尚需验证；本轮只能展示模拟 UI，不迁移真实在线表格。

## UI 2.0 的验收方式

独立演示采用中文、商务蓝白灰、浅色/深色/跟随系统和各端适配。网页保留独立业务搜索、内部标签页、抽屉详情与完整新建页；iPhone 使用原生导航与适合手机的卡片、分段详情和扫码场景。

先对照当前总指令整理验收清单，不声称恢复了未取得的历史“50项”或“23条”原编号文本。所有模拟通知、授权、扫描和业务结果明确标识演示。老板验收通过后，再另行授权把单个 UI 模块接入既有 API，并执行权限、库存、财务与幂等回归。
